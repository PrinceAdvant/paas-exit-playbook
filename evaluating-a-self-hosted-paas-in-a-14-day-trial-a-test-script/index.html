PaaS Exit Playbook

Evaluating a self-hosted PaaS in a 14 day trial: a test script

Two weeks is enough to know whether a self-hosted platform suits your team, as long as you test the boring parts and not only the first deploy. This is the script I follow.

Days 1 and 2: install and first app

Install on a fresh server using only the official docs. Time it. Deploy one real repository, not a hello world. Note every place where you had to read source code or an issue thread to get unstuck.

Days 3 and 4: databases

Create a Postgres database, connect the app, then take a backup and restore it to a new database. If restore is awkward, you will find out during an incident instead.

Days 5 and 6: domains and TLS

Attach two custom domains, one apex and one subdomain. Break DNS on purpose and see how the platform reports the certificate failure.

Days 7 and 8: team access

Invite a second person with limited rights. Check what they can see: logs, environment variables, other projects. Try to do something they should not be allowed to do.

Days 9 and 10: failure

Deploy a commit that crashes on start. Does the old version keep serving traffic? How quickly can you roll back? Fill the disk to 95 percent and see what warns you.

Days 11 and 12: upgrade

Upgrade the platform itself. Note downtime and whether apps restarted.

Days 13 and 14: exit

Export an app and run it with plain Docker elsewhere. If you cannot, that is lock-in you should price in.

Score each block from one to five and compare tools on the same script. For an example applied to two tools, see the Peon vs Coolify comparison. I work on Peon, an open-source self-hosted PaaS.

Practical notes on choosing, testing and leaving hosting platforms, written by a contributor to Peon (peon.sh), an open-source self-hosted deployment platform.
