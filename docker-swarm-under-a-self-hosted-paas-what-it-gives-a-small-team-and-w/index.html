Docker Swarm under a self-hosted PaaS: what it gives a small team and what it costs

Some self-hosted platforms use Docker Swarm to run apps across more than one server. Swarm is built into Docker, so it adds no extra install, but it changes how a few things behave.

What you gain

  • Placement across nodes. Services can be scheduled on any worker, with constraints such as "only on nodes labelled db".
  • Rolling updates. update_config with order: start-first starts the new task before stopping the old one.
  • Overlay networking. Containers on different machines talk over an encrypted overlay network by service name.
  • Secrets. Swarm secrets are stored encrypted in the raft log and mounted as files.

What it costs

  • Stateful services get harder. A volume is local to a node. If a database task moves to another node, its data does not follow. Pin stateful services with placement constraints.
  • Debugging spans machines. Logs and docker exec need to happen on whichever node runs the task.
  • Manager quorum. With three managers you can lose one. With one manager, losing it means losing control of the cluster, though running containers keep going.
  • Compose differences. Swarm ignores some Compose keys such as build and depends_on conditions, so files that work locally may need changes.

When one server is enough

If everything fits on one machine with headroom, plain Docker with Compose is simpler to operate and debug. Add nodes when you have a measured reason, such as isolating a database or needing more CPU for builds.
